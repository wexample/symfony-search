# Extraire et moderniser la recherche dans symfony-search

Opened: 2026-09-15
Updated: 2026-09-15
Author: agent:main

## But

Une recherche **transverse** dans `wexample/symfony-search`, dont les entités Doctrine ne
sont qu'un cas parmi d'autres — les pages routées en sont un second.

## Décisions actées

1. **`SearchResult` est une entité sans ORM.** `#[PseudocodeExport]`, pas de `#[ORM\Entity]`.
   Elle hérite de la standardisation : export `entity.ts`, repository front généré, vues =
   collections d'entités. Le legacy faisait déjà ça ; le faux `#[ApiResource]` ApiPlatform
   qui l'entourait est retiré.
2. **La route suit la convention entité** : `api/search-result/list`, pas `/_system/`.
   Le `SearchResultRepository.ts` généré la consomme sans câblage.
3. **symfony-forms dépendra de symfony-search** et y wrappera la recherche dans un field.
4. **SQL seulement.** Pas de `SearchBackendInterface`.
5. **Le scoring reste post-requête.** Filtrage SQL, ranking PHP sur `maxResults * 2`.
6. **Rôle minimum configurable** (`minimum_role`, `ROLE_ANONYMOUS` ouvre à tous).
7. **Front, routing, build d'assets : hors périmètre de cette tâche.**

## Déclaration par propriété (remplace la liste de champs)

Les natures de champ sont devenues des **attributs de propriété** — `#[SearchText]`,
`#[SearchReference]`, `#[SearchAmount]`, `#[SearchEmail]`, `#[SearchId]` — et sont les
mêmes objets que les anciennes classes `Class/Field/*`, supprimées. L'attribut de classe
`#[Searchable]` ne garde que ce qui vaut pour l'entité entière : `contexts`, `titleField`,
`subtitleField`, `route`, `icon`, `scoring`, `provider`.

Gains : le champ suit un renommage de propriété, et **un trait qui apporte une colonne
apporte la façon dont on la cherche**. Seules les entités portant `#[Searchable]` sont
lues, donc un trait peut porter l'attribut sans rendre cherchable tout ce qui l'utilise.

Reprises : `#[SearchIgnore]` sur la propriété redéclarée, ou `except: ['title']` sur la
classe pour qui ne veut pas la redéclarer.

**La dépendance inverse, refusée par l'outil.** J'avais fait porter l'attribut aux traits de
`symfony-helpers` en m'appuyant sur le fait que PHP le tolère : un attribut dont la classe
est absente ne casse rien, `getAttributes()` sans filtre le liste sans le charger. Techniquement
vrai, mais le contrôle de dépendances de la suite refuse l'import — `DEPENDENCY_VIOLATION`,
helpers important du code de search sans chemin déclaré, et il ne peut pas y en avoir : l'api
requiert helpers, search requiert l'api. Commit `88a5be5` annulé.

À la place, un champ nommé sur la classe peut se passer de dire sa nature : `fields: ['name']`
prend celle que sa colonne implique — `string`/`text` → texte, `decimal`/`float` → montant.
Tout le reste (date, booléen, enum) doit la dire, le registre refusant de deviner plutôt que
de deviner mal. Nommer la nature reste aussi la façon de changer les points par défaut :
`'body' => new SearchText(points: 5)`.

Les traits **de l'app** ou d'un package autorisé à nommer search peuvent toujours porter
l'attribut ; c'est seulement `symfony-helpers` qui ne le peut pas.

Vérifié par exécution en isolation : champ de trait + champ propre, trait seul suffisant,
`except` qui reprend, `#[SearchIgnore]` qui reprend — le mécanisme reste bon, seul son usage
dans `symfony-helpers` était interdit.

## Scoring par entité (réimplémenté)

Ce que mon premier attribut avait perdu de network : des points **par champ**, un champ qui
ne compte que si la requête a **la bonne forme**, un **contexte** qui pèse. Sur les sept
`searchResultBuildScore()` de network, six étaient le même code recopié autour de getters
différents ; la septième (`AccountingTransaction`) divisait la base par deux en `header` et
doublait le montant.

- `SearchQuery` connaît sa forme : `isNumeric()`, `getAmount()`, `isEmail()`.
- Les champs sont typés (`Class/Field/`) : `TextField`, `ReferenceField`, `AmountField`,
  `EmailField`, `IdField`, chacun avec `constrain()` (le SQL selon la forme) et `score()`.
  Déclarés avec `new` dans l'attribut — un argument d'attribut ne peut être qu'un
  constructeur, pas `Field::text()`.
- `SearchScore` est le builder fluent : `->text()`, `->reference()`, `->amount()`,
  `->email()`, `->id()`, `->inContext(ctx, factor)` ; chaque méthode porte le garde de sa
  nature. Vérifié par exécution : `15428` classe la facture (montant) devant le log (id),
  un texte reste muet sur un nombre, un fragment ne score pas un email, le facteur de
  contexte s'applique quel que soit l'ordre d'appel.
- `#[Searchable(scoring: X::class)]` nomme une classe `SearchScoringInterface` (service
  taggé, servi par un locator) qui reçoit le même builder. `weight` a disparu.
- Acolyte : `scoring:` sur l'attribut → `src/Search/{Entity}SearchScoring.php`
  (`filestate-symfony` + `wex-addon-dev-php`), comme `provider: true`.
- Une requête dont la forme ne convient à aucun champ déclaré ne lance aucun SQL.

## Où vivent les morceaux du front

Tout ce qui connaît l'API de recherche est dans ce package : `assets/vue/search/search-box`,
`assets/vue/search/search-result`, `assets/vue/form/fields/entity-search-input`, et la shape
`assets/css/shapes/_search-box.scss`. Ils étaient d'abord dans design-system, qui ne dépend
pas de search — un package y nommait donc le repository `searchResult` et les paramètres
`search/context/type` sans connaître celui qui les sert. Même défaut que le champ de
formulaire, corrigé de la même façon.

Ce qui reste dans design-system : `vue/partials/bar`, la cartouche, qui ne sait rien de la
recherche et dont l'entête dit déjà qu'un résultat y rentre comme n'importe quoi d'autre.
La dépendance ne lit que dans un sens : search requiert design-system.

## Limites connues, assumées

- `FETCH_FACTOR = 2` : un terme qui matche mille lignes n'en classe que les deux cents
  premières que la base a renvoyées. C'est le plafond du principe, pas un bug.
- `RouteSearchProvider` ne voit que `#[IsGranted]` : une page protégée par un pattern de
  firewall ou par un test dans l'action est listée.
- Collision possible si une entité s'appelle `Route` (type `route` déjà pris par le provider).
- Le titre d'une page est le nom de route humanisé, faute de traduction des routes. Ce que
  ça donne en vrai, vu dans la démo : « Wexample design system generic content media ».
  C'est lisible et c'est laid ; le câbler sur symfony-translations est la suite évidente.
- `assets/data/entity/search_result.json` n'a pas de clé `package`, là où
  `symfony-money` porte `"package": "@wexample/symfony-money"`. Sans elle, une app
  régénère l'entité chez elle au lieu de l'importer du package npm. À remplir quand le
  front arrivera, pas avant : il n'y a pas encore de `package.json` ici.
- Le filtre des routes internes porte sur le **nom** (`_profiler_*`, `_system_*`), pas sur
  le chemin. Un chemin en `/_…` dont le nom ne commence pas par `_` passe — et c'est
  voulu : les pages `/_design_system/…` de la démo sont du contenu, pas de la plomberie.
